# PR body and individual comment operations

## Summary

Provide closed GitHub operations for updating a pull request body, reading an individual comment, and adding an eyes reaction. All operations use the plugin's protected GitHub App credentials and repository/action policy.

## Behavior

1. The public tools are `github_pr_update_body`, `github_issue_comment_get`, `github_pr_review_comment_get`, `github_issue_comment_reaction`, and `github_pr_review_comment_reaction`. Configuration uses their unprefixed action names. All five require explicit global or repository allowances. Repository exclusions and action denials take precedence; neither the eight-action read profile nor the thirteen-action write profile includes them. The package version is `0.1.0` and configuration version is `1`.
2. Each tool requires an exact `repo` owner/name. Body update requires a strict integer `number` from 1 through 2147483647 and a string `body`. Comment operations require a strict integer `comment_id` from 1 through 9223372036854775807. Booleans and string integers are rejected. Unknown fields, credential arguments and arbitrary HTTP overrides are rejected.
3. `pr_update_body` replaces the entire body of an existing open, closed or merged PR. An empty body clears it. The plugin limit is 65536 Unicode code points, independently of GitHub's server limits. NUL and surrogate code points are forbidden; line breaks and tabs are permitted. No title, state, base branch, labels or other PR fields are changed.
4. Body update verifies the PR number and canonical repository before one body-only PATCH using Pull requests write permission. Missing PRs, issue numbers, redirects, and mismatched or unverifiable targets are refused. A successful response contains only the PR `number` and canonical `html_url`. An accepted response with an inconsistent number or repository is uncertain.
5. Body updates have no compare-and-swap precondition. A concurrent editor can overwrite this change or be overwritten by it. The caller must account for this when replacing existing text.
6. `issue_comment_get` reads a conversation comment by ID using Issues read permission. GitHub's shared issue-comment namespace covers comments on both issues and PRs; its endpoint permits Issues read or Pull requests read. `pr_review_comment_get` reads an inline PR review comment by ID using Pull requests read. The namespaces are distinct; this does not authorize issue-number operations on PRs.
7. Comment reads return only `id`, `body`, `user` fields `id`, `login`, `type`, validated `html_url`, and `issue_url` or `pull_request_url`. The returned comment ID must match the request and actor metadata must be well formed. Raw diff hunks and unrelated fields are omitted.
8. A comment's parent API URL must identify the same canonical repository and a positive number, with no redirect, query or fragment. Conversation comments use the `/issues/{number}` parent resource and review comments use `/pulls/{number}`. The HTML URL must match that repository, parent number and comment ID on `https://github.com`: conversation comments permit `/issues/{number}#issuecomment-{id}` or `/pull/{number}#issuecomment-{id}`; review comments require `/pull/{number}#discussion_r{id}`. The validated upstream URL is preserved.
9. `issue_comment_reaction` and `pr_review_comment_reaction` add one `eyes` reaction to the selected conversation or review comment using Issues write or Pull requests write respectively. There is no reaction-content selector, removal operation or reaction-list operation. Success contains only reaction `id`, fixed `content: eyes`, actor `user` fields `id`, `login`, `type`, and boolean `created`. HTTP 201 means created and HTTP 200 means already present.
10. Each mutation sends at most one write. Explicit GitHub rejection returns a sanitized denial. A timeout, server failure, malformed accepted result or otherwise unverifiable post-mutation result returns `uncertain_outcome` without an automatic retry or fallback credential path. Credentials are redacted from all results.
11. Protected-file checks, canonical repository verification, strict arguments, scoped tokens and repository/action authorization apply to these operations as to the rest of the catalog. A policy allowance makes the registered tool callable by agents with the `github_app` toolset; policy does not distinguish individual callers or add a separate approval workflow.
12. Comment IDs remain exact integers in the native Hermes path. Provider-side schema acceptance and numeric precision above 2^53 are not guaranteed by native tests. Callers must not round IDs or use strings to evade strict validation.

GitHub endpoint references: [update a PR](https://docs.github.com/en/rest/pulls/pulls#update-a-pull-request), [read a conversation comment](https://docs.github.com/en/rest/issues/comments#get-an-issue-comment), [read a review comment](https://docs.github.com/en/rest/pulls/comments#get-a-review-comment-for-a-pull-request), [react to a conversation comment](https://docs.github.com/en/rest/reactions/reactions#create-reaction-for-an-issue-comment), and [react to a review comment](https://docs.github.com/en/rest/reactions/reactions#create-reaction-for-a-pull-request-review-comment).
