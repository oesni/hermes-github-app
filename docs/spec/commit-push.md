# Publish local Git commits

## Summary

Agents can commit changes in their own checkout and publish those existing commits through `github_git_push`, without receiving GitHub credentials or sharing a filesystem path with the host. The operation preserves commit identities and history while applying the plugin's repository and action policy.

## Behavior

1. **Explicit permission.** The public tool is `github_git_push`; its configuration action is `git_push`. It requires an explicit global or repository `allow_actions` entry. The grant permits both new-branch publication and fast-forward updates: denying `branch_create` does not remove the new-branch capability of `git_push`. Repository exclusions and global or repository action denials win. The read profile retains eight actions and the write profile retains thirteen. Neither includes publication. Package version `0.1.0` and configuration version `1` remain unchanged.
2. **Commit locally, then publish.** The caller creates ordinary Git commits in its own checkout. Publication preserves their exact object IDs, authors, committers, messages, trees and parent relationships. It does not stage files, create replacement commits, amend commits or infer a commit message. Uncommitted and untracked changes are not published. Successful publication does not create or merge a PR; those remain separate operations.
3. **Closed request.** Every call supplies `repo`, `branch`, `commit_sha`, `expected_head_sha` and exactly one of `bundle_base64` or `bundle_path`. `repo` is the selected exact owner/repository. `branch` is a short branch name under the existing branch-name restrictions, never a refspec or revision expression. `commit_sha` is the full 40-character hexadecimal SHA-1 ID of the exact commit to publish, normalized to lowercase. SHA-256 repositories, abbreviations and revision expressions are refused. `expected_head_sha` is explicitly `null` when creating a branch, or the exact expected existing branch head when updating it. Omitting it is invalid. The null value is a tool argument, not a relaxation of the configuration's prohibition on YAML nulls. No remote URL, host-file input, credential, force flag, deletion, tag, arbitrary ref or Git option is accepted.
4. **Bounded bundle input.** The bundle uses Git bundle version 2, advertises exactly `refs/heads/<branch>` at `commit_sha`, and is at most 32 MiB (33554432 bytes) before base64 encoding. `bundle_base64` must be canonical standard base64 with no whitespace. A bundle may be self-contained, or for an existing branch have exactly one prerequisite matching `expected_head_sha`. The latter lets a small update avoid retransmitting old repository history; the host must obtain that prerequisite from the selected repository. Other prerequisites, missing history, corrupt objects and a requested object that is not a commit are refused. The entire imported repository, including a fetched prerequisite's shallow base snapshot, is limited to 256 MiB of decoded Git objects and 100000 objects. Git child processes have a 64 MiB per-file limit, which also limits fetched pack files, and a 512 MiB address-space limit. A small incremental update can be refused because its base snapshot exceeds these limits. The bundle header must fit 4096 bytes, including the prerequisite subject; multiple prerequisites are refused even when ordinary Git accepts such a bundle. There is no chunked upload session or automatic fallback when these limits are exceeded. A new branch can instead be created at an existing base with separately authorized `github_branch_create`, followed by a bounded incremental push. This reduces transmitted history, not the required base-snapshot size. Those are separate operations: if publication fails, the base branch can remain.

5. **One branch.** A call can publish only the named branch at `commit_sha`. Bundles advertising extra refs or tags are refused. No tag update, branch deletion, mirror push, multi-branch push, unrelated ref update or force rewrite is supported. Repository content is data: publication does not run repository hooks, check out files, fetch submodules or upload Git LFS objects. A committed LFS pointer remains a pointer; any referenced LFS object must already be available through a separate authorized workflow.
6. **Create only when absent.** `expected_head_sha: null` requires the target branch to be absent. If another writer creates it before publication is accepted, the call refuses rather than replacing it, even if it has the requested commit. Publication into an otherwise empty repository is permitted when all policy and GitHub prerequisites pass.
7. **Update only the expected history.** A non-null `expected_head_sha` requires the branch to exist at exactly that commit and that commit to be an ancestor of `commit_sha`. A divergent update is refused even when the caller correctly names the existing head. The expected-head condition must hold atomically when GitHub accepts the branch update; a concurrent change cannot be overwritten. This guards the value at acceptance, not whether the branch temporarily changed and returned to the same value. A branch may change again after successful publication.
8. **Credentials and destination.** The host verifies the canonical repository and uses only the configured App installation and a token restricted to that repository with Contents write permission. Secrets never appear in agent arguments, results or mounted files. The destination is GitHub.com for the authorized repository. No ambient Git credentials, personal token, alternative installation, redirect destination or broader-permission fallback is used. Protected-file checks and action policy apply again before publication.
9. **Repository protections.** `git_push` permits any branch, including the default branch; there is no plugin branch allowlist. Denying `pr_merge` does not prohibit direct pushes. Administrators must use GitHub branch protections when PRs are required. GitHub remains authoritative for repository rules, branch protections, permission grants and acceptance of uploaded content. An administrator must keep the App free of applicable bypass grants, as described in the configuration contract. The plugin never adds a bypass or elevates token permissions. Changes requiring additional permissions, including workflow-file changes, may be rejected. An allowed publication may trigger GitHub Actions or other repository automation; denying `pr_merge` does not prevent downstream automation from reacting to a push.
10. **Refusal and uncertainty.** Invalid input, policy denial, isolation failure, unavailable host prerequisites, mismatched remote head and non-fast-forward updates are distinct from success. An explicit remote refusal does not trigger another push. A timeout, interruption or unverifiable result after publication begins is reported as `uncertain_outcome`, without claiming no side effects or automatically retrying. Callers must inspect the remote branch before deciding what to do next. Cancellation cannot undo a publication already accepted. Uploaded objects may exist remotely even if a branch update is rejected; atomicity concerns the requested branch reference.
11. **Sandbox file input.** `bundle_path` is an absolute path of at most 4096 characters to a nonempty regular file in the active terminal backend. Control characters, surrogate characters and a final symlink are refused. The explicit publication grant includes a fixed file-read command through the public terminal dispatcher and host Git child processes. The plugin forwards the original task context to read bounded chunks; it does not open the path in the plugin host process or expose credentials to the terminal. Terminal dispatch follows the configured terminal backend; a local backend reads host files with that backend's existing access. The public dispatcher may invoke this fixed reader even if the calling profile does not enable the terminal toolset. The plugin does not promise that nested dispatch applies model-level tool checks or hooks. The active task ID, a working terminal backend and `python3` in that backend are required. Missing context or dispatcher refuses this input form rather than selecting a default environment. Changes detected in file metadata or the complete content digest, missing bytes, malformed or truncated terminal output and terminal failures return `bundle_unavailable` before publication. Transfer has a 120-second deadline, commands have at most 30 seconds each, and no failed transfer is retried. Low terminal output limits or slow backends can prevent a path transfer below the bundle size limit. Direct base64 remains available without terminal dispatch.
12. **Results and deadlines.** Success returns `branch`, `sha`, `previous_sha` (null for creation) and `created`. The returned SHA is exactly the requested commit, never a replacement commit. Publication has a 120-second operation deadline, separate from a preceding sandbox transfer. Publication requires a Linux host, Git 2.28 or newer and working address-space resource limits for every Git child; other platforms or missing limits refuse with `git_unavailable`. Missing prerequisites cause refusal, not installation or credential fallback. No result returns raw Git output, bundle contents or authentication material. A no-op update with the exact expected/requested head requires a self-contained bundle (Git cannot create an empty incremental bundle), leaves the branch unchanged and reports `created: false`.
